# 5179r - thread tools reach other devices (remote track; omo #12336, #14237, v5.1.63..v5.1.79)

Upstream of record: oh-my-openagent `packages/omo-senpi/src/components/thread` at `v5.1.79`, the cross-device leg.
The thread track's fragment (`5179.md`) owns the same-device tools and leaves the relay leg to this track.

`src/thread/remote/` is its own module behind the `RemoteThreadPort` seam, so the same-device thread tools stay as the
thread track wrote them:

- `mod.rs`: `<device>/<session>` addresses, `with_remote_thread_tools` (wraps `thread_send` and leaves every other tool
  as it was), the failure shape of the thread tools.
- `device_service.rs`: the port over the device service's local API v1: resolve the device (id, name or unique
  prefix), refuse this device, attach to the session, send one command, and map `route_unlisted` to `not_resumable`
  (#14237: a session that ended or parked elsewhere after it was listed).

`thread/native.rs` registers `thread_send` only when a device service has an endpoint on this device, so nothing
changes for a device without one.

Partial rows and why:

- `relay-control.ts`: sending (`thread_send`) is ported. The thread track's `RemoteControlLocator` hook (interrupt,
  close, rename, model, thinking level, messages and archive of a thread on another device) is not implemented: mhc-relayd
  carries only prompt, steer, follow_up, abort, set_model, get_state and close_session, and the native host registers no
  control tool yet. The intake admission of another device's rows (#13037) needs the wake path mhc-relayd does not carry.

Tests: `tests/remote_thread_tests.rs` (address grammar, routing to the port with local fallthrough, the failure shape).
